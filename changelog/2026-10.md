### ~23:49 IST (2026-10-02) — correction: the room server's media ports are published by ServiceLB, not `hostNetwork`

- **Actor:** agent (omp session). **Type:** git commit (this commit) — correcting the two entries
  directly above, appended rather than edited, per the changelog's append-only rule.
- **What the earlier entries got wrong:** they describe the LiveKit room server as running with
  `hostNetwork: true` and say "media is hostNetwork, not a Service". That was the *intended* design
  and it **never ran**.
- **What actually happened:** the Deployment was rejected by the API server —
  `pods "kirro-livekit-…" is forbidden: violates PodSecurity "baseline:latest": host namespaces
  (hostNetwork=true), hostPort (container "kirro-livekit" uses hostPorts 7880, 7881, 7882)`. The
  namespace label is `pod-security.kubernetes.io/enforce: baseline` (and `warn: restricted`), so the
  pod never scheduled and the Deployment sat at `0/1` with a `FailedCreate` on its ReplicaSet. The
  two firewall rules were already applied and are still correct — they are about which ports the
  node exposes, not about how the pod binds them.
- **Change:** the app repo (`Cheetos-gif/kirro`, `k8s/deployments.yaml` + `k8s/services.yaml` +
  `k8s/networkpolicy.yaml`) drops `hostNetwork`/`dnsPolicy` and adds a `LoadBalancer` Service,
  `kirro-livekit-media` (`externalTrafficPolicy: Local`, `7881/tcp` + `7882/udp`). k3s's ServiceLB
  binds those port numbers on the node — the mechanism Traefik already uses for 80/443 here — which
  satisfies ICE (the advertised port must equal the listening port, so an ordinary NodePort in
  30000-32767 would not do) while keeping the pod PSA-clean. `inventory/ports.yaml`'s `k8s_service`
  and `ingress` fields for 7881/7882 and `docs/ports.md`'s two rows are corrected to match.
- **Reason for choosing this over an exception:** the alternative was setting the `kirro` namespace
  to `privileged` (or giving the room server its own namespace). Relaxing a Pod Security level for
  one pod's convenience grants the same tolerance to every workload that lands in that namespace
  later, which is exactly the kind of standing permission this repository's S11/CLUSTER-001 work
  exists to avoid. A LoadBalancer Service needs no exception at all.
- **Also fixed, same change:** the NetworkPolicy for `kirro-livekit` allowed only Traefik and
  same-namespace peers. ServiceLB forwards media with the **caller's** source address preserved, so
  there is no in-cluster source to match; without an `ipBlock` rule the namespace's default-deny
  would have dropped every media packet, and the symptom would have been a connected call with no
  audio rather than an error.
- **Verification:** `kubectl get pods -n kirro` → `kirro-livekit-…` `1/1 Running`;
  `kubectl get svc kirro-livekit-media -n kirro` → `LoadBalancer` with `7881/TCP,7882/UDP` and a
  `svclb-kirro-livekit-media-…` DaemonSet pod `Running` in `kube-system`. External probes from a
  workstation: `138.201.157.147:7881` **open**, `:7880` **blocked** (deliberate — signalling goes
  through Traefik). End to end: a LiveKit client joined `wss://voice-kirro.upayan.dev`, published
  synthesized speech, and received the agent's spoken reply with both transcriptions —
  `PASS: production voice loop`.
- **Cost impact:** none. `LoadBalancer` on k3s is ServiceLB (a DaemonSet); no cloud load balancer is
  provisioned and nothing is billed.
- **Rollback:** revert the app-repo commit and hard-refresh the `kirro` Application. The firewall
  rules stay valid either way, since they describe the node's ports rather than the pod's.

### ~23:52 IST (2026-10-02) — opened `7881/tcp` and `7882/udp` for the `kirro` voice channel (WebRTC media)

- **Actor:** agent (omp session), continuation of the `kirro` voice-channel work above.
  **Type:** git commit (this commit) + `scripts/tf.sh apply` (Terraform, not ArgoCD).
- **Trigger:** the LiveKit room server in namespace `kirro` carries the browser's audio, and WebRTC
  media cannot traverse Traefik or any Kubernetes Ingress — only the signalling WebSocket can, and
  that arrives on 443 like every other `*.upayan.dev` host. Without these two rules a caller connects
  and hears nothing.
- **Change:** two inbound rules added to `hcloud_firewall.vps` in `terraform/firewall.tf` —
  `tcp/7881` and `udp/7882`, both from `0.0.0.0/0` and `::/0`. Matching entries added to
  `inventory/ports.yaml` (`status: live`) and the table in `docs/ports.md`. The app's ConfigMap sets
  `rtc.udp_port: 7882` deliberately — a **single muxed UDP port** rather than LiveKit's default
  50000-60000 range, so the internet-facing surface of this feature is two ports instead of ten
  thousand. `7881` is the WebRTC-over-TCP fallback for networks that block UDP.
- **Reason:** public by design, not an oversight: any browser that can reach
  `voice-kirro.upayan.dev` must also reach the media path, and the caller's address is not knowable
  in advance. Authorisation is the signalling room token — a LiveKit JWT signed with the key pair in
  the `kirro-voice` Secret, which the portal mints only for a signed-in Google user — not source-IP
  restriction. The media port itself is unauthenticated at the packet level, as WebRTC requires.
- **Verification:** `scripts/tf.sh plan` **without** this change reports "no differences"; **with**
  it, "Plan: 0 to add, 1 to change, 0 to destroy" listing exactly `7881` and `7882` added and no
  rule removed (the baseline-vs-change diff was compared directly, not assumed).
  `python3 scripts/check-ports.py` → "25 registry entries, no duplicates, no unregistered
  exposures, and the registry agrees with terraform/firewall.tf". `terraform fmt -check -recursive`
  clean, `terraform validate` → "Success! The configuration is valid."
- **Cost impact:** none — Hetzner firewall rules are free; no new billed resource.
- **Rollback:** remove the two rules from `terraform/firewall.tf`, revert the registry entries, and
  `scripts/tf.sh apply`. Voice media stops working; nothing else is affected. `git revert` the commit
  then apply is the ordered path — reverting git alone does **not** close the ports, because the
  firewall is applied by Terraform, not ArgoCD.

### ~23:34 IST (2026-10-01) — `kirro` gained persistent state: PVC `kirro-data` (1Gi, local-path) + one break-glass pod delete to verify a restart

- **Actor:** agent (omp session), owner question: "for prod wont i need to store the data somewhere?".
  **Type:** break-glass kubectl (pod delete) + live cluster change applied by ArgoCD from the *app's* repo,
  not this one.
- **Change:** `kirro-data` PVC created in namespace `kirro` (1Gi, `local-path`, RWO, `WaitForFirstConsumer`)
  and mounted at `/app/data` on the `kirro-core` Deployment, with `KIRRO_DATA_DIR=/app/data` and
  `securityContext.fsGroup: 10001` on the pod. These manifests live in `Cheetos-gif/kirro` (`k8s/`), applied

  hard-refreshed (annotate) to pick them up.
- **Reason:** `kirro-core` keeps declarations, the idempotency ledger and the decision log as JSON/JSONL on
  disk (this app has no database by design). Without a volume that state died with every pod. The
  `fsGroup` is not cosmetic: the image runs as uid 10001 and a fresh `local-path` volume is root-owned, so
  without it the container crash-looped at startup on `PermissionError: '/app/data/state'` — reproduced
  locally in Docker before the fix.
- **Also fixed in the app repo, same change:** `Store` never reloaded what it wrote (write-only
  persistence), and the API never passed it a directory, so even a mounted volume would have come up empty.
  `Store` now rehydrates on init, `DecisionLog` resumes an existing file so `seq` stays monotonic across
  restarts, and `app_factory` reads `KIRRO_DATA_DIR`.
- **Verification:** `kubectl get pvc -n kirro kirro-data` → `Bound`. Created `decl-6bc817af` through
  `https://api-kirro.upayan.dev`, deleted the `kirro-core` pod (`kubectl delete pod -n kirro -l
  app=kirro-core`) and let the Deployment replace it: `GET /declarations` still returned `decl-6bc817af`
  with its state intact, and `/log?declaration_id=…` returned 8 records with `seq` 1–8, no reset.
  Application `kirro` `Synced Healthy` throughout.
- **Cost impact:** one 1Gi `local-path` volume on the existing node (node-local, no billed Hetzner volume).
- **Rollback:** `git revert` the `Cheetos-gif/kirro` commit that added `k8s/pvc.yaml` and the mount
  (`d4b8861`), then hard-refresh the `kirro` Application. The PVC is `Delete` reclaim-policy, so removing it

### ~14:45 IST (2026-10-01) — `rankstack`'s API pod was replaced every few minutes: image-updater pinned the digest on the *live* Application and `root`'s selfHeal deleted it ~2 s later, oscillating the Deployment between two revisions

- **Actor:** agent (omp session), owner report: "debug why rankstack keeps crashing". **Type:** git
  commit (this commit) + break-glass hard-refresh of `rankstack` and `root`. **Prod:** the
  `rankstack-api` Deployment only — no application code was wrong and nothing in the app repo changed.
- **Symptom vs. reality:** the owner's view was "it keeps crashing". The container never crashed:
  pod `RESTARTS 0`, container log clean (`Application startup complete.` … `GET /health HTTP/1.1 200
  OK`), `curl https://api-rankstack.upayan.dev/health` → `200`. What was visible in the namespace
  every few minutes was a pod only minutes old plus `Readiness probe failed: Get
  "http://10.42.0.x:8000/health": dial tcp …: connect: connection refused` — the Deployment's *pod
  template* was being rewritten, so Kubernetes replaced the pod under it.
- **Measurement (Prometheus / kube-state-metrics, 6 h window):**
  `count(count by (pod) (count_over_time(kube_pod_info{namespace="rankstack"}[6h])))` → **306**
  distinct pods, against **1** (`mochi`) and **2** (`adhigrahan-radar`) — the only other apps still on
  the in-cluster write-back default; `changes(kube_deployment_status_observed_generation{namespace=
  "rankstack",deployment="rankstack-api"}[6h])` → **134** (~22 template rewrites/hour, one pod each);
  `max_over_time(kube_deployment_status_replicas_unavailable{…}[6h])` → **1**, i.e. windows with zero
  available replicas. Not cosmetic churn — real gaps in service.
- **Root cause (one sentence):** `argocd-image-updater` was writing its digest pin
  (`spec.sources[0].helm.parameters`: `image.repository` + `image.tag=edge@sha256:b52699…`) onto the
  **live** `rankstack` Application every 2 min (its `write-back-method` annotation was absent, which
  defaults to `argocd`/in-cluster), while `root` — the app-of-apps that manages every Application
  under `k8s/argocd/` with `selfHeal: true` + `ServerSideApply: true` — deleted that field within
  seconds because git does not carry it; the chart therefore rendered `image.tag` as `edge` or
  `edge@sha256:b52699…` depending on which controller won the race, and the Deployment flipped
  between revisions 1232 (`edge`, RS `rankstack-api-68f96b657`) and 1231 (`edge@sha256:b52699…`, RS
  `rankstack-api-689d8cc6dc`), replacing the API pod on every flip.
- **Evidence (all timestamps UTC):**
  - Polling `.spec.sources[0].helm.parameters` and the Deployment image every 3 s from 08:49:33 to
    08:54:29: the params appear **exactly twice** — 08:50:29 and 08:52:30, once per updater cycle —
    and are gone in the next sample (<5 s later). `image.tag` value:
    `edge@sha256:b52699f221249c6ae6d62bf4b4488767e2b56ad34a528f4fd5716676cb9733ce`.
  - Same object with `--show-managed-fields`: the only field manager after 08:50:31 was
    `argocd-controller` (the SSA applier, i.e. `root`'s selfHeal sync); image-updater's ownership of
    the field is gone — what "written, then force-taken and dropped" looks like.
    `.metadata.generation` moved 35953 → 35974 across that 3-minute window.
  - `argocd-image-updater` log, same cycle every 2 min, same digest each time:
    `Setting new image to …/api:edge@sha256:b52699…` → `Committing 1 parameter update(s) for
    application rankstack` → `Successfully updated the live application spec`. Identical output every
    cycle is the tell: the write never survives.
  - `kubectl -n rankstack get rs -l app=rankstack-api` → revisions 1231 and 1232 both live, carrying
    the two images above. `rankstack` Application sync history ids 1929–1935, ~2 min apart, with
    **unchanged revisions on every entry** (`automated: true`) — the app kept syncing an unchanged
    commit because its *parameters* kept changing.
  - `rankstack-mongo-rs-init` (Sync hook, wave 1) is deleted and re-created on each of those syncs —
    a second pod per cycle from the same loop, not a separate bug.
  - Ruled out first: no KEDA `HTTPScaledObject`/HPA in the namespace, no CronJob touching it, zero
    container restarts, Mongo `rs.status()` PRIMARY, and no `rankstack`-related commit in this repo
    since 2026-09-28 — every write was in-cluster.
- **Why the in-cluster write-back cannot work for this app (the actual bug class):** `rankstack` was
  set up deliberately with "zero write-back" (2026-09-24 entry — image-updater patches the
  Application object, no git write). That is only sound for an Application **nothing else
  reconciles**. Every explicit Application under `k8s/argocd/applications/` *is* reconciled by `root`
  with `selfHeal`, so image-updater and `root` were fighting over one field indefinitely: one writes
  it, the other deletes it, twice a minute, and the Deployment follows whichever won. It is the same
  in-cluster mechanism that left an orphaned `spec.source` behind on 2026-09-24 (SSA field-ownership
  gap), which needed a break-glass `kubectl patch` to clear.
- **Change:** `k8s/argocd/applications/apps/rankstack.yaml` — the four annotations that move the pin
  into git: `write-back-method: "git:secret:argocd/git-creds-updater"`, `write-back-target:
  "helmvalues:/k8s/apps/rankstack/values/image.yaml"`, `git-branch: main`, `git-repository:
  git@github.com:upayanmazumder/cluster.git`; plus `$values/k8s/apps/rankstack/values/image.yaml`
  appended as the **last** `helm.valueFiles` entry (later files win), and the stale "zero write-back,
  no git write" comment replaced with the incident. New file
  `k8s/apps/rankstack/values/image.yaml` — updater-managed `image.repository`/`image.tag`, seeded with
  the digest that was live (`b52699f…`, still what `:edge` resolves to, so the first updater pass
  should be a no-op commit). Separate file on purpose: the updater re-marshals whatever it writes, and
  `prod.yaml` is hand-authored and comment-annotated. `AGENTS.md`: the image-automation rule now says
  a `root`-managed Application must use git write-back, with this incident as the reason — the old
  text recommended exactly the arrangement that caused it.
- **Break-glass (logged here; nothing else was written by hand):**
  `kubectl -n argocd annotate app rankstack argocd.argoproj.io/refresh=hard --overwrite`, and the same
  for `root`, so both re-read `main` without waiting for the ~3 min poll. The read-only investigation
  and the Prometheus queries are not break-glass.
- **Reason:** git write-back — what the `apps` ApplicationSet apps and every other digest-tracked app
  here already do — rather than adding `ignoreDifferences` to `root` or excluding this Application
  from root's scope. Those two would leave live state permanently different from git (this repo's core
  invariant) and would keep a pin that is invisible in review. Its own values file keeps the updater's
  rewrite away from the hand-authored overlay, and the pin now survives a rebuild from git alone.
- **Verification (local, pre-push):** `python3 scripts/check-app-paths.py` → OK, 30 paths / 16 app
  directories accounted for (this is also the check that the new `valueFiles` entry exists);
  `bash scripts/helm-template-all.sh` → 5/8 rendered with the 3 vcap skips by design, and the rendered
  `rankstack-api` image is `ghcr.io/upayanmazumder/rankstack/api:edge@sha256:b52699…`, so the new
  value file is picked up and wins over the chart default; `yamllint -c .yamllint` clean on both
  changed files; the live `:edge` digest re-resolved against ghcr with an anonymous token →
  `docker-content-digest: sha256:b52699…`. **Live confirmation lands in the entry above once the
  updater's next cycle and a no-churn window have been observed.**
- **Cost impact:** none — same containers and resource requests; this removes pod churn, adds nothing.
- **Rollback:** `git revert` this commit (drops the write-back annotations and the `image.yaml`
  valueFile; delete `k8s/apps/rankstack/values/image.yaml` if the updater re-created it). That returns
  the app to the arrangement described above, i.e. the flapping — so roll back only if the git
