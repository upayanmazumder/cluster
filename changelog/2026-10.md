### ~22:54 IST (2026-10-03) — correction: `write-back-target` is `kustomization`, not `kustomize`

- **Actor:** agent (omp session). **Type:** git commit (this one).
- **What happened.** The kirro image automation merged in #45 used
  `write-back-target: "kustomize:/k8s"`. That value is not recognised by argocd-image-updater
  (v0.17.0): an unrecognised target is not rejected, it is taken as a **plain file path**, so the
  first successful write-back — which the deploy key landing enabled — committed a file literally
  named `kustomize:/k8s` at the root of `Cheetos-gif/kirro` instead of pinning the digest into
  `k8s/kustomization.yaml`. Log evidence: the commit's own message reports the intended digest, and
  its diff is a new file whose name is the annotation value.
- **Fix.** `kustomization:/k8s` (the documented keyword), which is otherwise identical: a
  repository-root-relative path to the directory holding `kustomization.yaml`.
- **Why it was not caught earlier.** The digest *did* resolve and the push *did* succeed once the
  deploy key was installed, so the pipeline looked healthy — the failure was in the shape of the
  artifact, not in any error. The bogus file is removed in the app repo.
- **Verification:** the stray `kustomize:/k8s` file is gone from `Cheetos-gif/kirro`; the next
  updater pass should commit `digest: sha256:...` into `k8s/kustomization.yaml` as
  `noodle <noodle@upayan.dev>`.
- **Cost impact:** none.
- **Rollback:** `git revert <sha>` — but reverting restores the wrong keyword.

- **Actor:** agent (omp session), owner instruction. **Type:** git commit (this one). **One owner action

- **What changed.** The `kirro` Application carried no image automation, and its own comment explained
  why: the only write-back credential, `argocd/git-creds-updater`, is a deploy key scoped to *this*
  repo, while kirro's manifests live in `github.com/Cheetos-gif/kirro`. Deploys therefore tracked

  git could not reproduce the cluster.

  repo's `k8s/kustomization.yaml` (the file ArgoCD actually renders): `image-list` +

  which one to write into — the ambiguity the old comment described as unsolvable.

  cannot push to `Cheetos-gif/kirro` however it is configured. `argocd/git-creds-noodle` is a new
  ed25519 keypair whose public half is a **write deploy key on `Cheetos-gif/kirro`**, titled `noodle`

  `k8s/platform/argocd-image-updater/noodle/secrets.sops.yaml` — its own file rather than appended to
  that directory's `secrets.sops.yaml`, because it is a different scope from the rest — and registered
  with the existing ksops generator.
- **Owner action required — the key is not installed yet.** The cluster account has `push` but not
  `admin` on `Cheetos-gif/kirro`, and adding a deploy key needs admin. Until the public key above is

  Cloudflare Access, no IP allowlist and no client certificate — the only control is the database
  password. It deliberately does **not** carry the mitigations v2's entry gates on (pg_hba
  restriction, non-superuser application role, per-person read-only roles): v1's schema and code
  expect `app_user` to *own* the database, so those are not drop-in. Recorded in the port's registry
  entry and in the runbook's "Security posture" section.
- **Verification (pre-merge):** `render-all` 27/27 dirs, `kubeconform` 0 invalid of 165,
